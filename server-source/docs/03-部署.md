# 03 · 部署

**操作步骤在 [`deploy/README.md`](../deploy/README.md) 里（NAS 一步步的版本）。这份文档只讲为什么这样部署，
以及动手前必须知道的坑。**

## 1. 形状

一个容器，两个命名卷，没有外部依赖：不需要 Postgres/Redis，不需要 worker，不需要构建工具链。

| 卷 | 容器内路径 | 内容 |
| --- | --- | --- |
| `ebookd_db` | `/data/db` | SQLite 数据库（含 WAL） |
| `ebookd_library` | `/data/library` | 内容寻址的原文件、封面、上传临时区、回收站 |
| `ebookd_imports` | `/data/library/imports` | 批量导入的落地目录（只读挂载可选的 `/import`） |

镜像基于 `node:24-bookworm-slim` 多阶段构建，`npm ci --omit=dev` 后**没有任何 `.node` 文件**，
以非 root 用户运行。这个前提由 CI 的 `image-dependencies` job 每次推送验证（见 `01-架构.md` §1.1）。

## 2. 三个必须知道的坑

1. **`/data/db` 绝不能放在 `/mnt/c`（9p）或 SMB 共享上。** SQLite 的 WAL 依赖可用的建议锁，
   在 9p/SMB 上拿不到锁的后果不是"变慢"，而是**数据库损坏**。用命名卷；确实要把书库放共享目录时，
   只把 `/data/library` 换成 bind mount（原文件是一次性追加写的，放共享上只是慢）。
2. **生产模式缺密钥直接拒绝启动。** `EBOOK_JWT_SECRET` 与 `EBOOK_MASTER_KEY` 必填，
   compose 里用 `${VAR:?}` 强制。生成：`node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`。
3. **bootstrap admin 的随机密码只在首次创建时打印一次。** 首启务必看日志；用完从日志轮转里清掉那一行。

## 3. 配置

全部环境变量见 [`server/.env.example`](../server/.env.example)（20 项，除密钥外都有合理默认）。
最常动的几个：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `EBOOK_BIND` / `EBOOK_PORT` | `0.0.0.0` / `8787` | compose 里映射为 `EBOOK_BIND:EBOOK_PORT → 8787` |
| `EBOOK_DATA_DIR` / `EBOOK_LIBRARY_DIR` | `./data/db` / `./data/library` | 容器内是 `/data/db`、`/data/library` |
| `EBOOK_MAX_UPLOAD_MB` | 512 | 单次上传上限；反代也要放同样的 body 限制 |
| `EBOOK_FILE_RETENTION_DAYS` | 7 | 删掉/替换后，字节还要在盘上留多久才可回收。**小容量 NAS 上这是唯一的磁盘旋钮**，设 0 表示"下一趟就回收" |
| `EBOOK_SWEEP_INTERVAL_HOURS` | 6 | 保留扫描的频率。幂等，调大只是晚点腾出磁盘 |
| `EBOOK_TRUST_PROXY` | false | **只有反代可信时才开**，否则 `X-Forwarded-For` 可被伪造 |
| `EBOOK_ALLOW_REGISTRATION` | false | 自助注册默认关闭，账号由管理员创建 |

端口默认 **8787**（开发机上 8000 已被占用）。手机在同一局域网联调时用 `http://<局域网 IP>:8787`。

## 4. 手机访问与 HTTPS

明文 HTTP 传的是你的账号密码和整本书。**不要把 8787 直接映射到公网**，三个可接受的方案按推荐程度：

1. **只走内网 + 组网**（WireGuard / Tailscale）：不开放任何公网端口，客户端不需要证书。
2. **反向代理 + 证书**（compose 里注释掉的 Caddy / 群晖与威联通自带的反代 + Let's Encrypt）：
   `EBOOK_BIND=127.0.0.1`，反代独占 443 转发到 8787，配合 DDNS 域名。记得设 `EBOOK_TRUST_PROXY=true`。
3. 至少：限制来源 IP + 长随机密码（服务端已内建 5 次失败锁 15 分钟）。

> **缺口**：`deploy/README.md` §5 引用了 `deploy/Caddyfile`，但该文件**尚未入仓**；
> 反代配置目前只有 §5 里那 3 行示例。

App 侧 https 分支的代码是写全的，切换 https 只是改 URL，不是改代码。

## 5. 健康检查、备份与升级

- **健康检查**：compose 定义了对 `/api/v1/meta` 的 healthcheck（`/health` 不碰库，只证明进程活着）。
- **备份**：数据库运行时不能直接 `cp`（WAL 里可能有未合并数据）。冷备停服 + `tar` 卷，
  或热备不可变的 `/data/library`。命令见 `deploy/README.md` §3。
- **升级**：`git pull` + `docker compose up --build -d`；迁移在启动时自动执行，只向前且带校验和，
  **改动已执行过的迁移会导致启动失败**（这是刻意的）。要加字段就新增迁移文件。

## 6. 这条通道的验证现状

- 镜像与数据存活在 M7 用 `docker compose up --build` 实测过：容器健康，
  `docker compose down && up` 之后数据仍在（卷验证通过）。
- **CI 不构建镜像**：每次发布前要手工跑一遍 `docker compose up --build`，
  否则容器健康只能依赖上一次 M7 的结论。
- 首次部署后建议按 `deploy/README.md` §8 的排障表逐项过一遍（缺密钥、`SQLITE_CANTOPEN`、迁移漂移等）。
